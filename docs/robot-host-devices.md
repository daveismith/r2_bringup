# Robot host: devices, udev rules and CAN interfaces

What the body Pi (`r2-body`, Raspberry Pi 5, Ubuntu 24.04, kernel `6.8.0-*-raspi`) has
installed outside the workspace so the droid's hardware comes up the same way on every
boot. None of these files are managed by this repository: they live in `/etc` and
`/boot/firmware` on the Pi and have to be recreated by hand on a fresh install. Their
exact contents are below. Recorded 2026-10-21.

| file | what it does |
|---|---|
| `/etc/udev/rules.d/90-spi0-no-autosuspend.rules` | keeps the SPI controller of the shoulder CAN chip powered |
| `/etc/udev/rules.d/91-odrive.rules` | lets `odrivetool` and the DFU flasher reach the ODrives over USB without root |
| `/etc/udev/rules.d/99-dualsense.rules` | lets the `input` group read the DualSense controller |
| `/etc/systemd/network/10-can-shoulder.link` | names the MCP2515 bus `can_shoulder` |
| `/etc/systemd/network/11-can-odrive.link` | names the USB candleLight bus `can_odrive` |
| `/etc/systemd/network/80-can.network` | brings `can_shoulder` up at 1 Mbit/s |
| `/etc/systemd/network/81-usbcan.network` | brings `can_odrive` up at 1 Mbit/s |
| `/boot/firmware/config.txt` (`dtoverlay=mcp2515-can0,...`) | declares the MCP2515 CAN chip on SPI |

`/etc/udev/rules.d/70-snap.snapd.rules` is generated by snapd and is not ours.

After adding or changing a udev rule: `sudo udevadm control --reload` and then either
replug the device or reboot (a rule with `ACTION=="add"` only runs when the device
appears). After changing a `.network` file: `sudo systemctl restart systemd-networkd`.

## The two CAN buses

| bus | hardware | driver | bitrate | used by | traffic (idle) |
|---|---|---|---|---|---|
| `can_odrive` | USB candleLight adapter (`1d50:606f`) | `gs_usb` | 1 Mbit/s | `ODriveInterface` in `urdf/ros2_control.xacro` (`can` parameter) | about 1 200 frames/s |
| `can_shoulder` | MCP2515 on `spi0.0`, 12 MHz crystal, interrupt on GPIO12 | `mcp251x` | 1 Mbit/s | `cyphal_service` (`interface` in `/etc/cyphal_service/cyphal.toml`), `ShoulderSensors` in `urdf/ros2_control.xacro` (`can_interface`) | about 210 frames/s |

**Stable names.** The kernel numbers CAN interfaces `can0`, `can1` in the order their
drivers probe, and that order is not fixed: until 2026-10-20 the MCP2515 always came up
first, but on the reboot of 2026-10-20 22:07 the USB adapter did, the names swapped, and
`cyphal_service` (then configured for `can0`) transmitted on the ODrive bus. So each bus
is renamed by its driver with a systemd `.link` file, to a name the kernel never hands out
itself (a rename onto `can0` could collide with the interface already holding it):

```ini
# /etc/systemd/network/10-can-shoulder.link
[Match]
Driver=mcp251x

[Link]
Name=can_shoulder
```

```ini
# /etc/systemd/network/11-can-odrive.link
[Match]
Driver=gs_usb

[Link]
Name=can_odrive
```

A `.link` file is applied when the device appears, so a change takes effect at the next
boot. Everything that opens a bus must use these names: the two `.network` files, `cyphal.toml`,
and both hardware interfaces in `urdf/ros2_control.xacro`. Installed 2026-10-21.

Check after a reboot:

```bash
for c in can_shoulder can_odrive; do echo "$c: $(basename $(readlink -f /sys/class/net/$c/device))"; done
# can_shoulder: spi0.0, can_odrive: the USB interface (4-2:1.0 or similar)
```

## `90-spi0-no-autosuspend.rules`

```
ACTION=="add", SUBSYSTEM=="platform", KERNEL=="1f00050000.spi", ATTR{power/control}="on"
```

Turns off runtime power management of the RP1 SPI controller (`1f00050000.spi`, the
`spi0` bus the MCP2515 sits on). With `power/control` at `auto` and no autosuspend delay,
the controller suspended after every transfer and resumed for the next, thousands of
times a second, which cost about 15 % of a core in `kworker/*-pm` threads (measured
2026-10-20). With `on` that load is gone. Added 2026-10-20.

Check: `cat /sys/devices/platform/axi/1000120000.pcie/1f00050000.spi/power/control`
prints `on`.

This does not touch the larger cost on the same bus, the MCP2515's interrupt thread
`irq/174-spi0.0`: about 22 % of a core at 2 MHz SPI (30 % at 10 MHz) for about 210
frames a second, because the level-triggered GPIO interrupt fires about 100 times per
frame. See the `config.txt` section.

## `91-odrive.rules`

```
SUBSYSTEM=="usb", ATTR{idVendor}=="1209", ATTR{idProduct}=="0d3[0-9]", MODE="0666", ENV{ID_MM_DEVICE_IGNORE}="1"
SUBSYSTEM=="usb", ATTR{idVendor}=="0483", ATTR{idProduct}=="df11", MODE="0666"
```

The first line opens the ODrive's own USB interface (`1209:0d30` to `0d39`) to every user,
so `odrivetool` works without `sudo`, and tells ModemManager to leave it alone (it would
otherwise probe the ODrive's serial port as a modem). The second opens the STM32 DFU
bootloader (`0483:df11`) that an ODrive presents while its firmware is being flashed.
Neither is needed for normal driving, which goes over CAN.

## `99-dualsense.rules`

```
KERNEL=="hidraw*", ATTRS{idVendor}=="054c", ATTRS{idProduct}=="0ce6", MODE="0660", GROUP="input"
```

Gives the `input` group read and write access to the Sony DualSense controller's
`hidraw` device (`054c:0ce6`), so `joy_node` can open it without root. The user running
the stack must be in `input` (`groups pi`).

## `80-can.network` and `81-usbcan.network`

```ini
# /etc/systemd/network/80-can.network
[Match]
Name=can_shoulder

[CAN]
BitRate=1000K
```

```ini
# /etc/systemd/network/81-usbcan.network
[Match]
Name=can_odrive

[CAN]
BitRate=1000K
```

`systemd-networkd` sets each interface to 1 Mbit/s and brings it up at boot. They match by
name, so they must use the `.link` names; with the kernel's `can0`/`can1` they would match
whichever bus probed first.

Check: `ip -details link show can_shoulder` (and `can_odrive`) shows `state ERROR-ACTIVE`
and `bitrate 1000000`.

## The MCP2515 overlay in `config.txt`

```
dtoverlay=mcp2515-can0,oscillator=12000000,interrupt=12,spimaxfrequency=2000000
```

(As of 2026-10-21 the Pi runs the test value `spimaxfrequency=10000000`, with the
2000000 line above it commented out; it is to go back to 2000000, see below.)

Declares the MCP2515 on `spi0` chip select 0 with a 12 MHz crystal and its interrupt on
GPIO12; `dtparam=spi=on` must also be set. The overlay asks for a level-low interrupt
(`interrupts = <12 8>`), and on this kernel that interrupt fires about 100 times per
received frame (each run finds nothing to do and costs about 9 us). Raising
`spimaxfrequency` to 10 MHz was tried on 2026-10-20: each run was barely shorter and
there were more of them, 30 % of a core against 22 %, so it goes back to 2 MHz. Next to try:
the same overlay with a falling-edge interrupt (`<12 2>`), watched for an hour for missed
frames; failing that, a second USB candleLight adapter for the shoulder bus.

Check after a reboot:

```bash
d=$(dirname $(grep -rl mcp2515 /proc/device-tree/ --include=compatible | head -1))
od -An -tu4 --endian=big $d/spi-max-frequency     # 2000000
grep spi0.0 /proc/interrupts                       # the interrupt count
```
